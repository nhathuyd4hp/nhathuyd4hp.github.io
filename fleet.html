FleetOps

A self-hosted platform that enrolls Windows and Linux machines across private networks, tracks their health, runs approved jobs on them and rolls out agent updates in stages. A FastAPI control plane keeps the record in PostgreSQL, hands commands to NATS JetStream, and talks to a Go agent that only ever dials out.

This is a design document, not a running system. Intervals and limits on this page are defaults, not measurements.

System at a glance

Admins and agents both reach the control plane through one TLS proxy on port 443. Nothing connects into an endpoint.

Decisions and trade-offs

  • A modular monolith, not microservices

    Gain: one image, one deploy, shared transactions (which the outbox needs) and simple local development.

    Cost: api and worker share a failure domain, and module boundaries hold only by convention: each module owns its tables.

  • PostgreSQL is the record; JetStream delivers, through an outbox

    Gain: no dual write. A job exists in PostgreSQL before any agent can receive it.

    Cost: an extra relay loop and an outbox table to prune; dispatch waits for the relay's next pass.

  • Agents dial out on :443, NATS over WebSocket

    Gain: works through NAT and strict firewalls, with no inbound ports and no VPN in phase 1.

    Cost: the proxy is the single ingress and a single point of failure; WebSocket adds a hop compared with native NATS on :4222.

  • A certificate and scoped NATS credentials per device

    Gain: a stolen credential reads only that device's commands and can be revoked on its own.

    Cost: running a small internal CA: issuing, renewing and revoking certificates.

  • Allowlisted operations instead of a remote shell

    Gain: small blast radius, typed parameters, and audit entries that say what actually happened.

    Cost: a new kind of task needs an agent release. The gated shell covers rare exceptions.

  • Heartbeats land in Redis; PostgreSQL gets state changes

    Gain: database writes do not grow with heartbeat frequency.

    Cost: a Redis restart loses last_seen, so the sweeper waits one full timeout before marking anything offline.

  • Signed releases, canary first, then waves

    Gain: a compromised server cannot ship a malicious agent, and a bad release stops at the canary group.

    Cost: signing is a manual step off the server; rollback depends on agents keeping the previous binary.

  • Docker Compose on one host

    Gain: one command to run it, and one machine to back up and reason about.

    Cost: no high availability. Losing the host means downtime until it is restored from backups.

From 10 test machines to 100+ endpoints

Nothing here has been benchmarked. Each endpoint costs one heartbeat request per interval, one NATS WebSocket connection and one durable consumer, and PostgreSQL is written only on change, so the same layout should carry the first hundred machines.

When measurements say it is needed, the next steps in order are: more api replicas behind the proxy (they are already stateless), a longer heartbeat interval or batched metric snapshots, a three-node NATS cluster, and WireGuard or a relay gateway for sites that block outbound WebSocket.
